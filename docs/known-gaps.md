# Known Gaps

This kit is an architecture and implementation guide for building a B2-backed neocloud platform. It is not a finished platform. This document is the honest inventory of what is intentionally missing, what is candidate material pending validation, what requires action outside the kit, and what is explicitly out of scope.

When a gap is closed, remove its entry from this document and reflect the change in `docs/source-of-truth.md`.

---

## 1. No Application Code

The kit contains zero executable code. There are no source files (no `.ts`, `.js`, `.py`, `.go`, etc.), no dependency manifests (no `package.json`, `requirements.txt`, `go.mod`), no test runners, and no CI configuration. The kit consists of documentation, prompts, context packs, and reference artifacts only.

**Impact:** Every PR listed in `docs/implementation-roadmap.md` is unbuilt. The 12-PR roadmap is the build plan, not a build log.

**To close:** Implement each PR in order, following `prompts/pr1-foundation.md` through `prompts/pr12-operational-hardening.md`.

---

## 2. API Contracts Are Target, Not Current

`docs/api-contracts.md` describes the **target** neocloud application API. No endpoint in that file is implemented. References to endpoints elsewhere in the kit (in the runbook, in prompts, in workflow recipes) describe the target shape, not a live API.

**Impact:** Code generated by following any prompt must match the target contracts; existing code (none) cannot be reused.

**To close:** Implement endpoints per PR scope. Update `docs/api-contracts.md` only if the implementation reveals a needed correction; do not drift the doc to match accidental implementation choices.

---

## 3. Partner API Details Require Backblaze Validation

The kit reflects Backblaze Partner API guidance as understood at the time of writing. Some specifics require direct confirmation with Backblaze before production use:

- Exact Partner API region codes accepted by `b2_create_group_member` (`us-east`, `us-west`, `ca-east`, `eu-central` are documented in the kit but should be validated).
- SSO email constraints on the `memberEmail` value for managed Groups.
- Behavior of existing provider keys after a Group member is ejected.
- Whether `b2_reserve_trial_create_account` is appropriate for any production workflow, or only for trial provisioning.
- Rate limits on Partner API operations under production load.

**Impact:** Production provisioning code must be validated against the live Partner API behavior, not solely against this kit.

**To close:** Confirm with Backblaze account team. Update `docs/provisioning-and-partner-api.md` with confirmed details.

---

## 4. Postman Collection Is Candidate Material

`postman/Backblaze_B2_Postman_Collection_CORRECTED_v3.json` is a candidate B2 Native API reference. It is not the target neocloud application API contract. It has not been independently validated against the live Backblaze API in this kit.

**Impact:** Postman should be used for B2 API familiarity and request-shape reference only. It must not be used as a source-of-truth for the target neocloud platform API.

**To close:** Run the Postman review checklist in `postman/README.md` against the live Backblaze API and a sandbox operator account.

---

## 5. No Production Security Review

The kit codifies security principles (tenant isolation, key scoping, audit immutability, credential redaction in logs, minimum-capability keys). It does not constitute a security review.

**Impact:** Any implementation built from this kit must undergo independent security review before production use. The kit's golden rules are a starting baseline, not a substitute for review.

**To close:** Commission a security review covering: authentication and authorization model, tenant isolation enforcement, secret storage, audit log integrity, key lifecycle, data plane authorization, presigned URL scoping, and CSV ingestion idempotency. Address findings before production.

---

## 6. Billing Is Reference Architecture, Not Payment Processing

`docs/usage-reporting-and-billing.md` and the billing-related PRs describe how to compute charges from `usage_import_rows` and produce `billing_ledger` entries and export files. The kit does not include:

- Payment collection (no Stripe, no card handling, no ACH).
- Invoice delivery or formatting.
- Dunning workflows or collections.
- Tax calculation, jurisdictional rate tables, or exemption handling.
- Real-time payment posting or settlement reconciliation.

**Impact:** The billing layer produces export artifacts; downstream systems are responsible for invoicing and collection.

**To close:** Integrate the export format with a billing system of record. This is out of scope for the kit.

---

## 7. No Production Observability Stack

The kit defines structured JSON logging, a `/health` and `/health/ready` endpoint, and a `/admin/metrics` JSON endpoint. It does not deploy:

- Prometheus, Grafana, or any metrics backend.
- Alertmanager or any alerting infrastructure.
- Centralized log aggregation (no Loki, Splunk, Datadog).
- Distributed tracing (no OpenTelemetry pipeline).
- Synthetic monitoring or SLO dashboards.

**Impact:** The application emits structured signals; consuming them is a deployment-environment decision outside the kit.

**To close:** Wire the structured outputs into the operator's existing observability platform. Out of scope for the kit.

---

## 8. No Multi-Cloud Abstraction

The storage provider abstraction exists to support a mock provider for local development and a real B2 provider for production. It is not designed as a multi-cloud abstraction. The interface deliberately reflects B2-specific concepts (Groups, Partner API, customer accounts, application keys).

**Impact:** Adapting the kit to AWS S3, Google Cloud Storage, or Azure Blob would require significant rework — not just an interface swap.

**To close:** Out of scope. Multi-cloud is not a goal.

---

## 9. No Migration Tooling

The kit does not include tooling to migrate data from another storage provider into a neocloud B2 deployment. Bucket-to-bucket copy, manifest reconciliation, large-scale rehydration, and bulk metadata import are not in scope.

**Impact:** Customer migrations require external tooling or one-off scripts.

**To close:** Out of scope. Build migration tools per customer engagement as needed.

---

## 10. Quota and Retention Schema Extensions

The canonical `docs/data-model.md` defines `projects.quota_policy` but does not specify a column-level schema for tenant-level aggregate quotas, retention deadlines, or per-tenant lifecycle metadata. Some operational flows (notably tenant deletion with retention window) assume schema extensions the operator must define.

**Impact:** Implementations may need to add:

- Tenant-level deletion timestamp / retention deadline tracking (column, separate `tenant_lifecycle_events` table, or composite status states).
- Tenant-level aggregate quota tracking if needed beyond project-level quotas.
- Bucket-level retention policy columns (the schema includes `buckets.retention_policy` as a placeholder JSON column — its contents are operator-defined).

**To close:** Define operator-specific extensions in a customer overlay or in a follow-on PR. Document the chosen extension shape.

---

## 11. No Real Customer Onboarding Workflow

The kit describes the provisioning steps (`POST /admin/tenants`, Partner API calls, bucket creation, key creation) but does not include:

- Customer self-signup or self-service onboarding.
- Contract management, terms-of-service enforcement, or e-signature flows.
- Identity provider integration (the kit assumes dev tokens for local use; production identity is operator-defined).
- Email verification, account approval workflows, or automated welcome messaging.

**Impact:** Operators must integrate the provisioning API with their own onboarding pipeline.

**To close:** Out of scope. Operators wire `/admin/tenants` into their own onboarding system.

---

## 12. No Object-Level Compliance Features

The kit does not implement:

- B2 Object Lock policies or governance/compliance mode enforcement.
- Legal hold workflows.
- Cross-region replication (B2 accounts are single-region; multi-region is multiple accounts, not replication).
- Lifecycle rules (transition, expiration) beyond the `buckets.lifecycle_policy` placeholder field.
- CORS configuration.
- Event notification rules.

**Impact:** Workloads requiring these features must add them on top of the kit.

**To close:** Add per-feature implementation in dedicated PRs after PR 12. Each is a non-trivial feature.

---

## 13a. S3-Compatible API Limitations

Backblaze's S3-compatible API implements the most commonly used subset of AWS S3, not the full surface. Workloads that depend on the following will NOT work via S3:

- SSE-KMS encryption — use SSE-B2 or SSE-C instead.
- Object tagging (`PutObjectTagging` / `GetObjectTagging`).
- IAM roles, STS, `AssumeRole`. Use B2 application keys directly.
- Website configuration / static website hosting.
- Browser-based POST uploads to presigned URLs.
- Object-level ACLs (objects inherit bucket ACL).
- SigV2 authentication — SigV4 only.

These are limitations of B2's S3 implementation, not the kit. They are documented for tenants in `docs/s3-compatible-api.md` §Explicitly NOT Supported.

The platform does not work around these — workloads that strictly require an unsupported feature should use the B2 Native API or a different storage backend.

## 14. Documentation-Implementation Drift Risk

Because the kit is documentation-only, there is no compiler or test suite to catch divergence between docs and code. As implementation begins, docs may drift from reality unless actively maintained.

**Impact:** Out-of-date docs are worse than no docs.

**To close:** Every PR that changes a public surface (API, schema, env var) must update the relevant doc. `docs/quality-gates.md` enforces this; reviewers must check it.
