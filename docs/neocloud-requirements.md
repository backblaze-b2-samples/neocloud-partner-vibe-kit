# Neocloud Requirements

## Problem statement

The original starter kit demonstrates basic B2 file operations. Neocloud providers need a storage control plane, high-throughput data plane, account/sub-account tenant isolation, provisioning, usage reporting, billing/chargeback, and operational hardening.

## Personas

- Platform admin
- Tenant admin
- Developer/service account
- Finance/billing user
- Support/operator

## Functional requirements

### Tenant and storage-account management

- Create tenant application record.
- Provision one or more B2 customer accounts/sub-accounts for the tenant.
- Associate accounts with Groups.
- Store region, alias/memberEmail, S3 endpoint, and provider account metadata.
- Suspend/reactivate tenant workflows as local/composite access-control operations, not Partner API eject.
- Support multi-region customers through multiple storage accounts.

### Project management

Create project metadata, quotas, roles, and storage policy. Physical B2 file names are generated by the shared B2 file-name builder and stored in metadata.

### Object operations

Upload a file into a tenant/project context. The server selects the storage account, bucket, and physical B2 file name from trusted metadata. Tenant objects reside in buckets inside the tenant's provisioned B2 customer account/sub-account, and access is enforced through application metadata and auth context.

### Uploads

- Parallel file uploads.
- Multipart for files >= 100 MB.
- Retry/backoff and abort cleanup.
- Optional small-file packing/manifest/range-read workflow for small-object-heavy customers.
- Do not hard fail small files by default.

### Usage reporting and billing

- Durable usage event ledger.
- B2 usage CSV ingestion.
- Attribution by provider account/storage account first, then bucket ID/name, then internal metadata.
- Unattributed rows stored for review.
- Deterministic reports and CSV/JSON exports.

### Provisioning

Partner API must be enabled by the Backblaze sales/team process; customers cannot self-enable it. Groups must be enabled and created in the Backblaze website before the app links/selects them. Partner API is required for provisioning and ejecting customer accounts. Recommended account alias/memberEmail pattern: `<partner_customer_id>-<b2_partner_region>@<partner_storage_domain>`. The Neocloud alias is sent to Backblaze as `memberEmail`. Eject requires explicit operator confirmation because it is not normal suspension, does not delete the account, may leave existing provider application keys functional unless handled separately, and cannot be undone by re-adding the account through the Partner API.

## Non-functional requirements

- Scalability for at least 100 active tenants using provisioned B2 customer accounts/sub-accounts before requiring control-plane architectural changes.
- Resiliency, retries, idempotency.
- Observability and auditability.
- Metadata-based authorization.
- Local development with mock provider.
- Testability and reviewable PRs.
